## What we did

### Foundation (fully done — cascades to the whole app automatically)
- Sourced real Anton + Archivo font files. Anton was a direct download; Archivo only ships as a variable font from Google, so the 6 static weights (400/500/600/700/800/900) were instanced from it with `fonttools varLib.instancer` (`wght=<N> wdth=100`). Files live in `src/assets/font/Anton/` and `src/assets/font/Archivo/`, registered in `App.js`'s existing `Font.loadAsync` call and in `src/utils/fontStyles.js`.
- **Found and fixed this session — a real bug that had been silently breaking Archivo bold/black text across the ENTIRE app since the fonts were first sourced (an earlier session, not this one):** the 6 instanced Archivo static-weight files all carried **identical internal font name-table metadata** (`fonttools varLib.instancer` doesn't rename a variable font's internal family/PostScript name per-instance unless told to). All 6 files claimed to be the same font ("Archivo SemiBold" / PostScript name `Archivo-SemiBold`) despite having genuinely different glyph outlines (confirmed via differing file sizes). On iOS, CoreText registers/dedupes fonts by PostScript name — loading 6 files that all claim the same PostScript name causes a collision, so only one weight's outlines actually end up rendering for *every* `fontFamily: 'ArchivoXXX'` request app-wide, regardless of which alias was requested. Fixed by rewriting each file's name table (nameID 1/2/3/4/6/16/17, both Mac and Windows platform records, plus `OS/2.usWeightClass`) with `fontTools` to give each weight a unique family/PostScript name matching its `fontStyles.js` alias (`Archivo400`...`Archivo900`). **Confirmed fixed after a full uninstall + `expo run:ios --device` reinstall** (a plain relaunch wasn't enough — iOS's CoreText font cache held onto the old broken registration; needed the reinstall to clear it).
- Remapped all ~130 color keys in `src/utils/themeColors.js` (both `Pink` and `Dark` variants) to the BTB palette, key by key — not a blanket find/replace, since many keys have specific semantic roles (error states, ratings stay gold, "order complete" stays green).
- Updated the central `src/utils/textStyles.js`: `H1`/`H2`/`H3` now get `fontFamily: Anton` + uppercase automatically. Since every screen's headline text already goes through the shared `TextDefault` component using these tokens, this alone gave the whole app (not just the 8 mocked screens) the Anton headline treatment for free — same leverage pattern as the color cascade.
- **Bottom tab bar** (`src/routes/index.js`'s `BottomTabNavigator`) redesigned to match the mockup's dark, text-only tab bar: `#0A0A0A` background (was white/`cardBackground`), icons removed entirely (the mockup has no tab icons at all, just uppercase text labels), active tab = white text + a small red (`currentTheme.primary`) 18×3px underline bar, inactive = gray (`#7A7A7A`, hardcoded — no existing theme token matches this specific dark-bar-only gray). Kept the same 4 tabs (Discovery/Restaurants/Search/Profile) — the mockup's tab bar shows a *different* set ("Home/Search/Orders/Account", no store-browsing tab, adds an order-history tab) which is an information-architecture difference, not just a style one, and wasn't something to silently change without a product call. `src/components/BottomTabIcon/` (both `BottomTabIcon.js` and `icons.js`) deleted entirely — confirmed nothing else in the codebase referenced it.
  - **First attempt used React Navigation's built-in `tabBarLabel`/`tabBarIcon` slots** to render text + underline together — on-device this rendered all 4 tabs visually identical with no underline at all. Root cause: the built-in label slot is sized for a single line of text and clips anything taller, silently dropping the underline `View`. **Fixed by replacing it with a fully custom `tabBar` render prop** instead of fighting the built-in slot: new `src/components/BottomTabBar/BottomTabBar.js` + `styles.js`, wired via `<Tab.Navigator tabBar={(props) => <BottomTabBar {...props} currentTheme={currentTheme} />}>`, handling focus state and `tabPress` navigation manually (the standard React Navigation custom-tab-bar pattern) — gives full control over layout with no slot-size assumptions to fight.

### Layout bugs found and fixed while verifying Home on-device
On-device testing of the new Home layout surfaced a pre-existing, unrelated layout bug plus one bug in the new code — worth knowing about since the same patterns exist elsewhere in the app:
- `src/screens/Main/styles.js`: the shared `flex` style (`{ flex: 1 }`, applied at every nesting level from the screen's `SafeAreaView` down to the scrollable content) had `flex: 1` **commented out**, leaving an empty style object. This looks like a pre-existing regression unrelated to the redesign — the screen apparently had never been run/verified on-device before this session. Restored `flex: 1`. Same file: `mainContentContainer` used `height: '100%'` nested inside `flex: 1` ancestors — a known-flaky RN/Yoga combination — switched to `flex: 1` throughout instead.
- `Main.js`'s `<ScrollView>` had no `style` prop at all. A `ScrollView` used as a flex child needs `flex: 1` set explicitly on itself (not just inherited) to get a bounded, scrollable viewport — added.
- **Root cause of a very confusing bug** (took a debug-color pass + React Native DevTools element inspection to actually nail down): `src/components/Main/CategoryChips/CategoryChips.js`'s `FlatList` had no `style` prop (only `contentContainerStyle`). An unstyled horizontal `FlatList` sitting in a column flex container next to another `flex: 1` sibling grows to fill remaining space rather than shrinking to its content — so it was splitting all the leftover screen height ~50/50 with the actual scrollable restaurant-list `ScrollView` below it, producing a large blank gap and squeezing real content into a small scrollable box. Fixed by giving the `FlatList` an explicit `style={{ flexGrow: 0 }}`. **Worth checking other horizontal `FlatList`/`SwiperFlatList` usages in the app for the same missing-`style` pattern if similar blank-space bugs show up elsewhere** (e.g. inside other flex-column screens).
- `Main.js` also swapped the RN-core `SafeAreaView` for `react-native-safe-area-context`'s version (see Home bullet above) and flipped `StatusBar` to `light-content` for the new dark header.
